# DEVELOPMENT — пошаговый гайд по сборке

Рабочий план для сценария из [`README.md`](./README.md): переводы в **одном
сервисе**, где перевод — это **одна транзакция** БД (двойная запись + статус +
outbox атомарно), а outbox идёт **только на нотификации** через Debezium.

Разбит на фазы: каждая заканчивается **проверяемым** результатом (тест или
`curl`), чтобы не строить всё сразу. Здесь — что и в каком порядке делать, с
сигнатурами и критериями готовности. **Логику движения денег пишешь сам** — это
суть практики; гайд даёт каркас и границы, а не готовое решение.

Легенда: 🎯 цель · 📁 файлы · 🔨 задачи · ✅ definition of done фазы.

## Фаза 0. Каркас и деньги

🎯 Проект собирается, тип денег корректен, пустой баланс читается.
📁 [ledger/money.go](./ledger/money.go), [store/postgres.go](./store/postgres.go).

**0.1 —** `Money`**: развести «входную сумму» и «величину проводки».**
Проводка знаковая (списание < 0), но входная сумма запроса всегда > 0.

- `Money` — сырой знаковый `int64` без валидации (проводки могут быть < 0);
- `NewAmount(minor int64) (Money, error)` — валидатор **входной суммы запроса**
  (строго > 0). Уже есть в [money.go](./ledger/money.go) — проверь, что
  используется в парсинге запроса, а проводки строятся из сырого `Money`.

**0.2 — баланс на пустом счёте.**
`SELECT SUM(amount)` без строк вернёт `NULL` → `Scan` в `int64` упадёт. В
[store/postgres.go](./store/postgres.go) `Balance` уже использует
`COALESCE(SUM(amount), 0)` — убедись, что так везде, где суммируешь проводки.

**0.3 — миграция.** [migrations/001_init.sql](./migrations/001_init.sql) уже
описывает `accounts`, `transfers`, `postings`, `outbox`, `processed_events`
(имена колонок outbox — под Debezium: `aggregatetype`, `aggregateid`). Накатывается
одним `make migrate`.

✅ **DoD:** `go build ./...` чисто; `make up && make migrate` проходит; тест
«создать счёт → прочитать баланс = 0» зелёный.

## Фаза 1. Транзакция перевода (ядро)

🎯 Перевод `A → B` проводится **одной локальной транзакцией**: две проводки +
статус в одном `COMMIT`. Сбой — полный откат.
📁 [store/postgres.go](./store/postgres.go), [ledger/ledger.go](./ledger/ledger.go).

**1.1 — реализуй** `Postgres.Transfer(ctx, req)` (сигнатура уже в
[store/store.go](./store/store.go)). В одной `tx`:

- валидация: счета существуют, одинаковая валюта, `from != to`, сумма > 0;
- проверка достаточности средств отправителя **под блокировкой** (см. 1.2);
- вставь **две** проводки с общим `transfer_id`: `-amount` у `from`,
  `+amount` у `to`;
- запиши `transfers.status = 'POSTED'`;
- `COMMIT`. Любая ошибка до коммита → `ROLLBACK`, вернуть доменную ошибку из
  [ledger/errors.go](./ledger/errors.go).

**1.2 — конкурентность (это ядро задачи):** «прочитал баланс в Go → списал»
даёт lost update. Сериализуй на уровне БД — выбери один способ:

- `SELECT ... FOR UPDATE` по строке счёта `from` (+ пересчёт баланса в той же
  tx), либо
- условная вставка/`CHECK`, не дающая уйти в минус, либо
- `SERIALIZABLE` + ретрай на `40001`.

**1.3 —** `Service.Transfer` ([ledger/ledger.go](./ledger/ledger.go)) — тонкая
обёртка над стором (домен не знает про SQL).

**1.4 — тесты фазы (memory-стор годится для happy-path):**

- happy-path A→B: баланс A `-amount`, B `+amount`, сумма проводок = 0, `POSTED`;
- недостаточно средств → ошибка, проводок нет, балансы не тронуты;
- сам себе / currency mismatch / сумма ≤ 0 → доменная ошибка, движения нет;
- **конкурентные** списания с одного счёта под `-race` не уводят в минус
  (на Postgres-сторе).

✅ **DoD:** тесты 1.4 зелёные под `-race`; на Postgres перевод виден
(`make psql`, посмотри `postings`); сумма проводок по паре счетов = 0.

## Фаза 2. Идемпотентность

🎯 Повтор запроса с тем же `Idempotency-Key` не создаёт второй перевод.
📁 [store/postgres.go](./store/postgres.go), [store/store.go](./store/store.go).

**2.1 — unique на** `transfers.idempotency_key` (уже в миграции). В `Transfer`:

- на конфликте по ключу — **не ошибка**, а «уже сделано»: верни существующий
  перевод. Отличай через `errors.Is(pgErr, unique_violation)` или
  `INSERT ... ON CONFLICT DO NOTHING` + повторный `SELECT`.
- сравни `request_hash` запроса с сохранённым: совпал → та же операция;
  разошёлся → `ErrIdempotencyConflict` (в API → `409`).
- опора на **unique-индекс**, а не на предварительный `SELECT` (две конкурентные
  вставки с одним ключом иначе обе пройдут).

**2.2 —** `GetTransferByIdempotencyKey` — реализуй для пути повтора.

**2.3 — тесты фазы:**

- два вызова с одним ключом **последовательно** → одна операция, один сдвиг;
- два вызова с одним ключом **конкурентно** (под `-race`) → ровно одна операция;
- тот же ключ с другими параметрами → `ErrIdempotencyConflict`.

✅ **DoD:** тесты 2.3 зелёные под `-race`; в БД по одному ключу — ровно одна
строка `transfers`.

## Фаза 3. HTTP API

🎯 Перевод инициируется по HTTP, идемпотентность по заголовку, корректные коды.
📁 [httpapi/](./httpapi/), [cmd/api/main.go](./cmd/api/main.go).

**3.1 — обработчики** ([httpapi/handlers.go](./httpapi/handlers.go)):

- `POST /accounts {currency}` → создать счёт;
- `GET /accounts/{id}` → баланс;
- `POST /transfers`: достать `Idempotency-Key` (нет → `400`); распарсить сумму
  как строку/целое (**не float**) через `NewAmount`; вызвать `Service.Transfer`;
  `POSTED` → `201` + тело; повтор с тем же ключом → `200`; конфликт параметров →
  `409`; бизнес-отказ → `422`; невалидный ввод → `400`;
- `GET /transfers/{id}` → состояние перевода;
- `GET /healthz` → ping БД.

**3.2 — middleware** ([middleware.go](./httpapi/middleware.go)): структурный
`slog` (метод, путь, статус, латентность); `Recover` уже есть. Единый формат
ошибки `{ "error": { "code", "message" } }`.

**3.3 — main** ([cmd/api/main.go](./cmd/api/main.go)): DSN из env, пул
соединений с лимитами, `store.NewPostgres`, `ledger.NewService`, роутер;
graceful shutdown уже заложен.

**3.4 — проверка** `curl`**:** создать два счёта, пополнить (см. ниже), перевод,
повтор с тем же ключом, посмотреть коды и баланс.

> Пополнение счёта: заведи отдельный сценарий (напр. проводка с технического
> `funding`-счёта или seed в миграции), иначе переводить нечего. Оставь простым.

✅ **DoD:** `make run` + `curl`-сценарий проходит; коды `201/200/409/422/400`
корректны; `GET /healthz` = 200.

## Фаза 4. Outbox → Debezium → exactly-once consumer

🎯 `TransferPosted` надёжно доходит до Kafka; консьюмер обрабатывает
exactly-once и **не трогает балансы**.
📁 [outbox/](./outbox/), `cmd/consumer/`.

**4.1 — запись outbox в транзакции перевода:** в `Postgres.Transfer` (фаза 1)
добавь вставку строки `outbox` (`aggregatetype='Transfer'`, `aggregateid` = id
перевода, `type='TransferPosted'`, `payload` = JSON перевода) **в той же tx**.
Проверь тестом: откат перевода ⇒ строки в outbox нет.

**4.2 — поднять CDC:** `make up-cdc && make connector`; `make connector-status`
= RUNNING; `make consume` показывает событие после перевода. Ключ = `aggregateid`.

**4.3 — консьюмер** (`cmd/consumer`): читает `outbox.event.Transfer`; в одной
tx: `INSERT INTO processed_events(event_id) ON CONFLICT DO NOTHING` + side-effect
(запись в read-model/лог нотификаций). Конфликт → событие уже обработано,
side-effect не повторяем. **Балансы консьюмер не трогает.**

**4.4 — тест:** доставь одно событие дважды → ровно один side-effect.

✅ **DoD:** событие видно в топике; двойная доставка = один side-effect;
`make down` не теряет уже проведённые переводы (они в БД).

> Fallback без Kafka: app-relay ([outbox/relay.go](./outbox/relay.go)) поллит
> `outbox` через `FOR UPDATE SKIP LOCKED`, публикует, ставит `published_at`.
> Держи его рабочим для среды без Debezium, но основной путь — CDC.

## Как отдавать на ревью

После любой фазы (или всего) — отдай каталог агенту-ревьюеру по
[VALIDATION.md](./VALIDATION.md). Приоритет проверки: корректность денег
(транзакция/двойная запись/конкуренция) > идемпотентность > outbox/exactly-once
> стиль.

## Частые грабли (свод)

- Баланс читается без блокировки, списание считается в Go → lost update под
  конкуренцией. Блокировка/ограничение на уровне БД.
- Идемпотентность на предварительном `SELECT` без unique-constraint → две
  конкурентные операции с одним ключом обе проходят. Опора на unique-индекс.
- outbox публикуется из кода после `COMMIT` вместо записи в tx → потеря события
  при краше между commit и publish.
- Консьюмер меняет балансы по событию → источник истины уезжает за Kafka. Деньги
  двигает только транзакция перевода; консьюмер — нотификации/read-model.
- `float` для денег где угодно, включая JSON → мгновенный fail.
- `SUM(amount)` без `COALESCE` на пустом счёте → `NULL` в `Scan`.
