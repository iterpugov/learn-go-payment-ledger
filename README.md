# Payment Ledger — переводы в одном сервисе (одна транзакция)

Сервис переводов с честной двойной записью. Все деньги живут в **одной**
Postgres-БД, поэтому перевод — это **одна локальная транзакция**: списание,
зачисление, статус и outbox-событие коммитятся атомарно. Либо всё, либо ничего.

Outbox здесь — **только для нотификаций/read-model**: он рассылает наружу
*свершившийся факт* (`TransferPosted`), а не двигает деньги. Балансы меняет
только транзакция перевода; консьюмер их не трогает.

Задача — удержать инвариант «деньги не теряются, не дублируются и не создаются
из воздуха» средствами одной БД: транзакция + двойная запись + идемпотентность,
а сверху — надёжная доставка событий через Debezium с exactly-once обработкой.

Ты пишешь код сам. Пошаговый план сборки (фазы, сигнатуры, SQL, критерии
готовности) — в [`DEVELOPMENT.md`](./DEVELOPMENT.md). Инструкция для
агента-ревьюера — в [`VALIDATION.md`](./VALIDATION.md).

> Это осознанно **одиночный** вариант: одна БД, одна транзакция. Распределённый
> сценарий (шарды, сага, оркестратор, компенсации, reconciliation) — отдельный,
> более сложный трек «дальше»; см. раздел [Куда расти](#куда-расти). Не тащи его
> сюда: пока БД одна, вся эта машинерия не нужна.

## Архитектура

```
                POST /transfers (Idempotency-Key)
                            │
                     ┌──────▼──────┐
                     │  API        │   одна БД `ledger`:
                     │  + ledger   │   accounts, transfers, postings, outbox
                     └──────┬──────┘
                            │  ОДНА транзакция:
                            │  2 проводки + статус + строка outbox
                            ▼
                     ┌─────────────┐
                     │  Postgres   │
                     └──────┬──────┘
                            │ outbox
                            ▼
              Debezium ─▶ Kafka ─▶ consumer (exactly-once)
                                        │
                                   нотификации / read-model
                                   (балансы НЕ трогает)
```

Компоненты:

- **API + ledger** — принимает переводы, атомарно проводит их одной транзакцией,
  отдаёт статус. Собственная БД `ledger`.
- **outbox + Debezium + consumer** — надёжная публикация лайфсайкл-событий
  перевода (`TransferPosted`) и exactly-once обработка на приёмнике. Это
  propagation факта, а не команда на движение денег.

Стенд — в [`deploy/`](./deploy/), команды — в [`Makefile`](./Makefile).

## Двойная запись в одной транзакции — читай первым

Перевод `A → B` на сумму `amount` — это **две проводки в одном COMMIT**:

- `debit A`: проводка на `-amount` по счёту A;
- `credit B`: проводка на `+amount` по счёту B;
- сумма двух проводок перевода = 0 → ledger всегда сбалансирован.

Баланс счёта — это `SUM(amount)` его проводок, а не отдельное изменяемое поле.
Проводки **append-only**: правок и удалений нет; «отмена» — это новые
компенсирующие проводки (в одиночном варианте они почти не нужны — транзакция
либо коммитится целиком, либо откатывается).

**Инварианты, которые нельзя нарушать никогда:**
- проводки перевода коммитятся атомарно (одна `tx`) — нет «списал, а зачислить
  не успел»;
- сумма всех проводок по всем счетам = 0;
- деньги — целое в минимальных единицах (или decimal), **никогда `float`**
  (в т.ч. в JSON);
- проводки append-only; баланс = сумма проводок.

## Транзакция перевода (ядро задачи)

`POST /transfers` в **одной** транзакции БД должен:

1. проверить/зафиксировать идемпотентность по `Idempotency-Key`
   (unique на `transfers.idempotency_key`);
2. проверить бизнес-правила: счета существуют, одинаковая валюта, не сам себе,
   сумма > 0, у отправителя хватает средств;
3. вставить **две** проводки (`-amount` у from, `+amount` у to) с общим
   `transfer_id`;
4. записать `transfers.status = 'POSTED'`;
5. вставить строку в `outbox` (`TransferPosted`) — **в той же транзакции**;
6. `COMMIT`.

Любой сбой на шагах 2–5 → `ROLLBACK`: ни проводок, ни события. Валидационный
отказ (шаг 2) — это `FAILED`/бизнес-ошибка, движения денег нет.

### Конкурентность (где реально ломается)

«Прочитал баланс в Go → посчитал → записал» под конкуренцией даёт lost update:
два параллельных списания оба увидят старый баланс и уведут счёт в минус.
Защита — **на уровне БД**, а не в Go:

- `SELECT ... FOR UPDATE` по строке счёта отправителя (сериализует списания),
  либо
- проверка достаточности прямо в `INSERT` (CHECK/условная вставка), либо
- `SERIALIZABLE` + ретрай на `40001`.

Выбери один способ и обоснуй. Тест на конкуренцию под `-race` обязателен.

## Идемпотентность

`Idempotency-Key: <uuid>` в заголовке обязателен. Unique на
`transfers.idempotency_key`:

- повтор с тем же ключом → возвращаем **ту же** операцию (`200`), не создаём
  вторую;
- тот же ключ с **другими** параметрами (проверка через `request_hash`) → `409`;
- опора на **unique-индекс**, а не на предварительный `SELECT` (иначе две
  конкурентные операции с одним ключом обе пройдут).

## Outbox + Debezium + exactly-once

**Где живёт outbox.** Строка `outbox` пишется в **той же транзакции**, что и
проводки перевода. Инвариант: событие уходит ⟺ перевод закоммичен. Никакого
«сначала commit, потом publish руками» — иначе краш между ними теряет событие.

**Доставка.** Debezium читает WAL БД `ledger`, гонит `outbox` в Kafka через
Outbox Event Router SMT (конфиг —
[`deploy/debezium-connector.json`](./deploy/debezium-connector.json)).
At-least-once.

**Exactly-once обработка.** Консьюмер (нотификации / read-model) дедупит по
`event.id` через таблицу `processed_events` **в той же транзакции**, что и
side-effect → эффективно exactly-once поверх at-least-once. Двойная доставка
одного события даёт один side-effect (докажи тестом).

**Консьюмер не меняет балансы.** Балансы двигает только транзакция перевода.
Outbox — это propagation свершившегося факта, а не команда на движение денег.

### Контракт таблицы `outbox` (Outbox Event Router)

| колонка | тип | смысл |
|---------|-----|-------|
| `id` | uuid | PK = event id (дедуп у консьюмера) |
| `aggregatetype` | text | `Transfer` → топик `outbox.event.Transfer` |
| `aggregateid` | text | id перевода (ключ партиции → порядок по агрегату) |
| `type` | text | `TransferPosted` |
| `payload` | jsonb | тело события |
| `created_at` | timestamptz | наблюдаемость |
| `published_at` | timestamptz NULL | для app-relay fallback; Debezium игнорирует |

> Fallback без Kafka: app-relay ([outbox/relay.go](./outbox/relay.go)) поллит
> `outbox` через `FOR UPDATE SKIP LOCKED`, публикует, ставит `published_at`.
> Держи его рабочим для среды без Debezium, но основной путь — CDC.

## HTTP API

stdlib `net/http` или chi. Без тяжёлых фреймворков.

| Метод | Путь | Назначение |
|-------|------|------------|
| `POST` | `/accounts` | создать счёт `{currency}` |
| `GET`  | `/accounts/{id}` | баланс |
| `POST` | `/transfers` | перевод `A → B` |
| `GET`  | `/transfers/{id}` | состояние перевода |
| `GET`  | `/healthz` | пинг БД |

**`POST /transfers`:**
- `Idempotency-Key: <uuid>` обязателен (иначе `400`).
- Тело: `{ "from_account", "to_account", "amount", "currency" }`; `amount` —
  строка/целое, **не float**.
- Коды: `201` — перевод проведён (`POSTED`), `200` — повтор с тем же ключом,
  `409` — тот же ключ с другими параметрами, `422` — бизнес-отказ
  (недостаточно средств, currency mismatch, сам себе), `400` — невалидный ввод.
- Ответ — JSON перевода с текущим состоянием.

Единый формат ошибки `{ "error": { "code", "message" } }`. Структурный лог
(`slog`). Graceful shutdown: дослушать инфлайт, остановить relay/консьюмер по
`ctx`.

## Обязательные тест-сценарии

1. **Happy-path A→B:** баланс A уменьшился, B увеличился на ту же сумму; сумма
   всех проводок = 0; статус `POSTED`; в `outbox` ровно одна строка.
2. **Недостаточно средств / валидация:** `422`, проводок нет, балансы не
   тронуты, события в outbox нет (транзакция откатилась).
3. **Идемпотентность API:** два вызова с одним ключом (последовательно и
   **конкурентно**) → одна операция, один сдвиг баланса, одно событие.
4. **Тот же ключ, другие параметры:** `409`.
5. **Конкурентные списания с одного счёта** под `-race`: баланс не уходит в
   минус, сумма проводок сходится.
6. **Атомарность outbox:** сбой при записи события ⇒ откат перевода (нет
   проводок и нет события).
7. **Exactly-once консьюмер:** двойная доставка события → один side-effect.
8. **Инвариант нуля под нагрузкой:** серия случайных переводов в N горутин;
   в конце сумма всех проводок = 0. Гоняется под `-race`.

## Definition of Done

- [ ] `go build ./...`, `go vet ./...` чисто; `go test ./... -race` зелёный.
- [ ] `make up && make migrate && make run` поднимает сервис на одной Postgres.
- [ ] Перевод — одна транзакция: проводки + статус + outbox атомарны.
- [ ] Двойная запись; сумма всех проводок = 0; баланс = `SUM(postings)`. Нигде
      нет `float` для денег.
- [ ] Конкурентное списание защищено на уровне БД; счёт не уходит в минус.
- [ ] Идемпотентность по `Idempotency-Key` (unique-индекс); `409` на конфликт
      параметров.
- [ ] Outbox пишется в одной транзакции с переводом; событие доходит до Kafka;
      консьюмер exactly-once, балансы не трогает.
- [ ] API отвечает корректными кодами; graceful shutdown работает.

## Куда расти

Когда одиночный вариант собран и крепко покрыт тестами — можно вводить
распределённость как **отдельный трек** (осознанно и по одной сложности за раз):

- деньги в **двух шардах** (разные БД) → общей транзакции больше нет;
- перевод становится **сагой** с оркестратором, suspense-счетами и
  компенсациями; появляются durable-состояние, воркер добивания, lost-ack;
- внешний **rail** (ненадёжный получатель) и **reconciliation** как
  предохранитель.

Тогда каждый паттерн осмыслен, потому что ты уже почувствовал, где именно
ломается одна транзакция. Но это не для этого README — здесь БД одна.

## Подсказки (если застрял — не читай сразу)

<details>
<summary>Почему outbox не должен двигать деньги</summary>

Если баланс меняет консьюмер по событию, источник истины уезжает за Kafka:
нельзя синхронно ответить «недостаточно средств», а любой дубль/потеря события
становится потерей/задвоением денег, а не пропущенной нотификацией. Деньги
двигает транзакция; outbox лишь сообщает, что это произошло.
</details>

<details>
<summary>Почему баланс нельзя читать без блокировки</summary>

«Прочитал баланс в Go, вычел, записал» под конкуренцией = lost update: два
списания видят старый баланс и оба проходят, счёт уходит в минус. Сериализуй на
уровне БД (`FOR UPDATE` / условная вставка / `SERIALIZABLE` + ретрай).
</details>

<details>
<summary>Почему outbox пишется в той же транзакции</summary>

Если публиковать событие из кода после `COMMIT`, краш между коммитом и publish
теряет событие навсегда. Запись строки `outbox` в той же транзакции связывает
факт и его анонс: доставку берёт на себя Debezium/relay из таблицы.
</details>
