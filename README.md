# Payment Ledger — боевой сценарий (распределённая сага)

Сервис переводов, устроенный как в платёжке: деньги живут в **разных шардах**,
атомарного коммита между ними нет, часть переводов уходит во **внешний rail**,
а сверх всех автоматических гарантий стоит **reconciliation**. Задача —
удержать инвариант «деньги не теряются, не дублируются и не создаются из
воздуха» в условиях, где одна транзакция уже не спасает.

Это не «сначала простой, потом сложный» — сразу боевой сценарий. Базовые
механики (double-entry, идемпотентность, outbox) здесь не отдельные этапы, а
кирпичи внутри саги.

Ты пишешь код сам. Решения в каталоге нет намеренно. Пошаговый план сборки (фазы,
сигнатуры, SQL, критерии готовности) — в [`DEVELOPMENT.md`](./DEVELOPMENT.md).
Инструкция для агента-ревьюера — в [`VALIDATION.md`](./VALIDATION.md).

## Архитектура

```
                         POST /transfers (Idempotency-Key)
                                    │
                             ┌──────▼──────┐
                             │  API + Saga │  orchestrator DB:
                             │ Orchestrator│  saga, saga_step, outbox
                             └──┬───┬───┬──┘
              reserve/confirm │   │   │ commit          send/poll
                    ┌─────────▼┐  │  ┌▼─────────┐   ┌──────▼──────┐
                    │ shard-a  │  │  │ shard-b  │   │ external    │
                    │ (money)  │  │  │ (money)  │   │ rail (stub) │
                    └──────────┘  │  └──────────┘   └─────────────┘
                                  │
                     outbox ─▶ Debezium ─▶ Kafka ─▶ consumer (exactly-once)
                                                         │
                                            reconciliation ◀─ rail statement
```

Компоненты (могут жить в одном или нескольких бинарях — на твой выбор):

- **API** — принимает переводы, отдаёт статус.
- **Orchestrator** — durable-состояние саги, гонит шаги и компенсации, воркер
  добивает незавершённые саги. Собственная БД (`orchestrator`).
- **shard-a / shard-b** — независимые Postgres со счетами и проводками. Между
  ними нет общей транзакции.
- **rail (stub)** — намеренно ненадёжный внешний получатель.
- **outbox + Debezium + consumer** — надёжная публикация лайфсайкл-событий
  перевода и exactly-once обработка на приёмнике.
- **reconciliation** — фоновая сверка ledger с выпиской rail и внутренних
  инвариантов.

Стенд — в [`deploy/`](./deploy/), команды — в [`Makefile`](./Makefile).

## Двойная запись через inter-shard suspense — читай первым

Ключ ко всей задаче. Раз счета в разных шардах, «списал у A, зачислил B» нельзя
сделать одной проводкой. Чтобы double-entry не сломался, каждый шард **всегда
локально сбалансирован** через технические **suspense/clearing-счета** (аналог
nostro/vostro между банками):

- на `shard-a`: `debit user_A` / `credit interbank_suspense_A` → сумма проводок
  на A = 0;
- на `shard-b`: `debit interbank_suspense_B` / `credit user_B` → сумма на B = 0;
- глобально `interbank_suspense_A (+amount)` и `interbank_suspense_B (-amount)`
  гасят друг друга → сумма проводок по **всем** шардам = 0.

Suspense-счета — это «мост» между шардами и одновременно якорь для сверки:
reconciliation обязан проверять `balance(suspense_A) == -balance(suspense_B)`.
Для rail роль моста играет `rail_suspense_A`, который сверяется с выпиской rail.

**Инварианты, которые нельзя нарушать никогда:**
- сумма всех проводок по всем шардам = 0;
- каждый шард локально сбалансирован в любой момент между шагами саги;
- деньги — целое в минимальных единицах или decimal, **никогда `float`** (в т.ч.
  в JSON);
- проводки append-only: компенсация — это новая проводка, а не удаление/правка.

## Сага (оркестрация)

Оркестратор хранит состояние в своей БД и **явно** вызывает шаги. Каждый шаг —
локальная идемпотентная транзакция в своём участнике. Общего коммита нет.

### Машина состояний перевода

```
                 reserve(from)         commit(to)/send(rail)      confirm(from)
   CREATED ──────────────▶ RESERVED ───────────────▶ APPLIED/SENT ─────────▶ POSTED
      │                        │                          │
      │ validation failed      │ commit/reject failed     │ (rail timeout: остаёмся SENT,
      ▼                        ▼                          │  идемпотентный ретрай + recon)
    FAILED               COMPENSATING ──release(from)──▶ REVERSED
```

- `FAILED` — отказ **до** любого движения денег (валидация): нет счёта, currency
  mismatch, самому себе, сумма ≤ 0, недостаточно средств. Проводок нет.
- `POSTED` — сага доведена до конца, деньги проведены.
- `REVERSED` — деньги успели частично сдвинуться (`RESERVED`/`SENT`), но операцию
  пришлось откатить компенсирующими проводками.

### Шаги — внутренний перевод (A → B)

1. `reserve(from)` на shard-a: `user_A → interbank_suspense_A`. Идемпотентно по
   `(saga_id, "reserve")`.
2. `commit(to)` на shard-b: `interbank_suspense_B → user_B`. Идемпотентно по
   `(saga_id, "commit")`.
3. `confirm(from)` на shard-a: финализация резерва. → `POSTED`.

Компенсация: если `commit(to)` не удался/завис — `release(from)` на shard-a
возвращает резерв (`interbank_suspense_A → user_A`) → `REVERSED`.

### Шаги — внешний перевод (A → rail)

1. `reserve(from)` на shard-a: `user_A → rail_suspense_A`.
2. `send(rail)` → `SENT`. Rail отвечает `ACCEPTED` / `REJECTED` / **таймаутом**.
   Идемпотентно по `external_ref`.
3. `ACCEPTED` → `confirm(from)` → `POSTED`. `REJECTED` → `release(from)` →
   `REVERSED`. **Таймаут** → остаёмся `SENT`, повторяем идемпотентно; если долго
   не разрешается — доводит reconciliation.

### Требования к саге

- **Durable-состояние** (`saga`, `saga_step`), а не в памяти. После рестарта
  оркестратора незавершённые саги подхватываются и доигрываются.
- **Только вперёд или только назад.** Нельзя застрять в `RESERVED`/`SENT`
  навсегда — воркер с таймаутом (`FOR UPDATE SKIP LOCKED`) добивает до
  терминального состояния.
- **Идемпотентность каждого шага и компенсации** по `saga_id` (для rail — по
  `external_ref`). Полагайся на unique-ключ шага в БД, а не на «кажется, уже
  делали».
- **Lost-ack.** Ответ участника может потеряться, хотя шаг выполнился
  (`commit(to)` прошёл, но подтверждение не дошло). Ретрай/компенсация обязаны
  это обнаружить (идемпотентная проверка), а не зачислить/вернуть повторно.

## Идемпотентность (три уровня)

1. **API.** `Idempotency-Key` → unique на `saga.idempotency_key`. Повтор с тем же
   ключом возвращает ту же сагу, а не создаёт вторую. Тот же ключ с другими
   параметрами → `409`.
2. **Шаг саги.** unique `(saga_id, step)` в ledger шарда → повторный вызов шага
   не задваивает проводки.
3. **Rail.** `external_ref` → повторная отправка не создаёт второй внешний
   платёж.

## Outbox + Debezium + exactly-once

**Где живёт outbox.** У распределённого перевода нет одной денежной транзакции,
поэтому лайфсайкл-события (`TransferPosted`, `TransferReversed`) публикует
**оркестратор** — пишет строку в `outbox` в **той же транзакции**, что и переход
саги в терминальное состояние. Инвариант прежний: событие уходит ⟺ переход
закоммичен.

**Доставка.** Debezium читает WAL БД `orchestrator`, гонит `outbox` в Kafka через
Outbox Event Router SMT (конфиг — [`deploy/debezium-connector.json`](./deploy/debezium-connector.json)).
At-least-once.

**Exactly-once обработка.** Консьюмер (нотификации / read-model) дедупит по
`event.id` через таблицу `processed_events` **в той же транзакции**, что и
side-effect → эффективно exactly-once поверх at-least-once. Двойная доставка
одного события даёт один side-effect (докажи тестом).

**Консьюмер не меняет балансы.** Балансы двигает только сага в шардах. Outbox —
это propagation свершившегося факта, а не команда на движение денег.

### Контракт таблицы `outbox` (Outbox Event Router)

| колонка | тип | смысл |
|---------|-----|-------|
| `id` | uuid | PK = event id (дедуп у консьюмера) |
| `aggregatetype` | text | `Transfer` → топик `outbox.event.Transfer` |
| `aggregateid` | text | id перевода (ключ партиции → порядок по агрегату) |
| `type` | text | `TransferPosted` / `TransferReversed` |
| `payload` | jsonb | тело события |
| `created_at` | timestamptz | наблюдаемость |

## Reconciliation — предохранитель последней инстанции

Фоновый джоб, который **не доверяет** ни саге, ни outbox, а сверяет источники
истины и чинит расхождения. Идемпотентен к повторному запуску.

1. **Внутренняя целостность:** сумма всех проводок = 0; `balance(suspense_A) ==
   -balance(suspense_B)`; для каждого `POSTED` есть корректный набор проводок;
   нет `RESERVED`/`SENT` старше SLA.
2. **Внешняя сверка** `SENT`-переводов с выпиской rail (метод rail «отдать
   принятые `external_ref` за период»):
   - есть `SENT`, есть в выписке → доводим до `POSTED`;
   - есть `SENT`, нет в выписке и вышел таймаут → компенсируем → `REVERSED`;
   - нет у нас, есть в выписке (rail принял, мы потеряли) → алерт + дозачисляющая
     проводка, чтобы ledger сошёлся с реальностью.
3. Каждое расхождение — в `recon_exception` (`open`/`resolved`). Повторный прогон
   не создаёт дублей исправлений.

## HTTP API

stdlib `net/http` или chi. Без тяжёлых фреймворков.

| Метод | Путь | Назначение |
|-------|------|------------|
| `POST` | `/accounts` | создать счёт `{shard, currency}` |
| `GET`  | `/accounts/{id}` | баланс |
| `POST` | `/transfers` | инициировать перевод (внутренний или на rail) |
| `GET`  | `/transfers/{id}` | состояние саги/перевода |
| `GET`  | `/healthz` | пинг всех трёх БД |

**`POST /transfers`:**
- `Idempotency-Key: <uuid>` обязателен (иначе `400`).
- Тело: `{ "from_account", "to_account" | "rail_ref", "amount", "currency" }`;
  `amount` — строка/целое, **не float**.
- Коды: `202` — сага принята (терминальное состояние может наступить асинхронно;
  клиент опрашивает `GET /transfers/{id}`), `200` — повтор с тем же ключом,
  `409` — тот же ключ с другими параметрами, `422` — бизнес-отказ (валидация →
  `FAILED`), `400` — невалидный ввод.
- Ответ — JSON перевода с текущим состоянием.

Единый формат ошибки `{ "error": { "code", "message" } }`. Структурный лог
(`slog`). Graceful shutdown: дослушать инфлайт, остановить воркер саги и
консьюмер по ctx.

## Обязательные тест-сценарии

1. **Happy-path A→B:** балансы сошлись; сумма проводок по обоим шардам = 0;
   каждый шард локально сбалансирован; состояние `POSTED`.
2. **Недостаточно средств / валидация:** `FAILED`, проводок нет, балансы не
   тронуты.
3. **Идемпотентность API:** два вызова с одним ключом (последовательно и
   конкурентно) → одна сага, один сдвиг баланса.
4. **Сбой `commit(to)`:** компенсация до `REVERSED`, резерв возвращён полностью,
   зависших suspense-остатков нет.
5. **Краш оркестратора между шагами:** после рестарта воркер доигрывает сагу до
   терминального состояния; ни одна не застряла в `RESERVED`/`SENT`.
6. **Lost-ack:** `commit(to)` выполнился, ответ «потерян»; ретрай/компенсация не
   задваивает и не теряет деньги.
7. **Rail timeout → recon:** перевод в `SENT`; reconciliation по выписке доводит
   до `POSTED` либо `REVERSED`; повторный прогон джоба — без новых исправлений.
8. **Rail «принял, мы потеряли»:** recon создаёт дозачисляющую проводку,
   фиксирует `recon_exception`, ledger сходится.
9. **Exactly-once консьюмер:** двойная доставка события → один side-effect.
10. **Инвариант нуля под нагрузкой:** серия случайных переводов (внутренних и на
    rail) с инъекцией сбоев; в конце сумма всех проводок = 0. Гоняется под
    `-race`.

## Подсказки (если застрял — не читай сразу)

<details>
<summary>Почему нельзя двумя схемами в одном Postgres вместо двух инстансов</summary>

Две схемы в одной БД делятся одной транзакцией — а именно потерю общего коммита
мы и моделируем. Шарды обязаны быть отдельными БД/соединениями, иначе сага
вырождается и вся задача теряет смысл.
</details>

<details>
<summary>Где ломается lost-ack</summary>

Наивная компенсация «вернуть резерв» поверх на самом деле успевшего `commit(to)`
= двойное движение денег. Компенсация должна сначала идемпотентно проверить
фактическое состояние шага (по `saga_id`), а не действовать вслепую по таймауту.
</details>

<details>
<summary>Зачем suspense-счета, если можно «просто списать и зачислить»</summary>

Без suspense каждый шард в промежутке между шагами разбалансирован (на A деньги
ушли в никуда, на B пришли ниоткуда), и инвариант «сумма проводок = 0» ломается
в наблюдаемом состоянии. Suspense держит каждый шард сбалансированным всегда и
даёт reconciliation точку сверки.
</details>
