# Инструкция для агента-ревьюера

Ты валидируешь чужое решение сценария из [`README.md`](./README.md): переводы в
**одном сервисе**, где перевод — это **одна транзакция** БД (двойная запись +
статус + outbox атомарно), outbox идёт через Debezium **только на нотификации** с
exactly-once консьюмером. Цель — не переписать код, а дать **честный конкретный
отчёт: где нарушены инварианты платёжного ядра и где отклонения от Go best
practices**. Автор учится — фидбек должен учить.

## Как действовать

1. Прочитай `README.md` (особенно про двойную запись в одной транзакции и
   конкурентность) и обязательные тест-сценарии.
2. Собери и прогони:
   ```
   go build ./...
   go vet ./...
   go test ./... -race -count=1
   ```
   Не собирается/не проходит → finding первого приоритета, приложи вывод.
3. Подними стенд и проверь вживую (не только тесты):
   ```
   make up && make migrate && make run
   ```
   `curl`-ом: создать два счёта, сделать перевод A→B, повторить с тем же
   `Idempotency-Key`, проверить состояние и коды. Если сдан CDC:
   `make up-cdc && make connector`, затем `make consume` — событие должно
   долетать до топика.
4. Читай доменное ядро и транзакцию перевода **до** вердикта. Каждый finding
   подкрепляй строкой кода или собственным проверочным тестом (держи его
   отдельно, код автора не правь).

## Чек-лист корректности (важнее стиля)

Для каждого пункта — **PASS / FAIL / РИСК** с файлом и строкой.

**Деньги и double-entry**
- [ ] Деньги — целое/decimal, **нигде не `float`** (парсинг, JSON, тесты).
- [ ] Перевод — **одна транзакция**: две проводки + статус + outbox коммитятся
      атомарно; сбой → полный `ROLLBACK` (нет проводок и нет события).
- [ ] Двойная запись: на перевод ровно две проводки (`-amount`/`+amount`), сумма
      = 0; баланс = `SUM(postings)`, а не отдельное изменяемое поле.
- [ ] Глобальный инвариант: сумма всех проводок по всем счетам = 0.
- [ ] Проводки append-only; правок/удалений нет.
- [ ] Баланс не уходит в минус; сумма > 0; currency mismatch и self-transfer
      отклоняются.

**Конкурентность / Postgres**
- [ ] Конкурентное списание защищено **на уровне БД** (`FOR UPDATE` / условная
      вставка / CHECK / `SERIALIZABLE` + ретрай на `40001`). «Прочитал баланс в
      Go, посчитал, записал» без блокировки — FAIL.
- [ ] `SUM(amount)` с `COALESCE` (пустой счёт не роняет `Scan`).
- [ ] Пул соединений с лимитами; ресурсы закрываются; `rows.Err()` проверяется.
- [ ] Миграция отражает double-entry (проводки — строки, не два поля на счёте).

**Идемпотентность**
- [ ] Unique на `transfers.idempotency_key`; повтор → та же операция (в т.ч.
      **конкурентно**), не вторая. Опора на unique-индекс, а не на
      предварительный `SELECT`.
- [ ] Тот же ключ с другими параметрами → `409` (через `request_hash`).

**Outbox / Debezium / exactly-once**
- [ ] Строка `outbox` пишется в **той же транзакции**, что и перевод; нет
      паттерна «commit, потом publish руками».
- [ ] Таблица `outbox` соответствует Event Router (`id`, `aggregatetype`,
      `aggregateid`, `type`, `payload`) — имена без подчёркиваний.
- [ ] Событие реально появляется в `outbox.event.Transfer`, ключ = `aggregateid`.
- [ ] Консьюмер дедупит по `event.id` через `processed_events` **в одной
      транзакции** с side-effect; двойная доставка → один side-effect (тест).
- [ ] Консьюмер **не меняет балансы** — только read-model/нотификации.

## Чек-лист Go best practices (вторично, но фиксируй)

- [ ] `context.Context` первым аргументом, проброшен до сторов, не игнорируется;
      relay/консьюмер останавливаются по ctx.
- [ ] Ошибки: `%w`, `errors.Is/As`, sentinel/типизированные ошибки, не строки;
      ошибки не проглатываются.
- [ ] Сторы за интерфейсами; домен не зависит от конкретной БД.
- [ ] Экспортируется только необходимое; публичный API документирован.
- [ ] Нет `panic`/`log.Fatal` в обработчиках; горутины не текут.
- [ ] `slog`; единый формат ошибки в API; нет утечки внутренних деталей в ответ.
- [ ] Тесты табличные где уместно, есть конкурентные; `t.Parallel()` без гонок.
- [ ] `go vet` и (если доступен) `staticcheck`/`golangci-lint` чисто.

## Формат отчёта

```
## Вердикт: PASS / PASS с замечаниями / FAIL

## Сборка, тесты, живой прогон
<вывод build / vet / test -race; результат curl-сценария>

## Нарушения инвариантов (критично)
1. [FAIL] <файл:строка> — <что> — <как это теряет/дублирует/создаёт деньги>
   Как проверил: <тест/рассуждение>
   Как чинить: <направление, без готового кода>

## Go best practices
- [замечание] <файл:строка> — <что> — <как принято>

## Что сделано хорошо
- <явно отметить сильные места — задача учебная>

## Приоритеты для следующей итерации
1. ... 2. ... 3. ...
```

## Тон и правила

- Приоритет: **корректность денег (транзакция/двойная запись/конкуренция) >
  идемпотентность > outbox/exactly-once > стиль**. Не топи в стилистике, если
  протекают деньги.
- Каждое утверждение — с доказательством (строка кода или свой тест). Не
  «возможно, гонка» — покажи где.
- **Не переписывай решение** и не редактируй файлы автора. Максимум — отдельный
  `review_*_test.go` для доказательства бага.
- Если инвариант проверить нельзя (не хватает кода) — так и скажи, не выдавай
  догадку за факт.
